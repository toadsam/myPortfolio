# 포트폴리오 자료 제작 목록

프로젝트 상세 페이지(`/resume` → 카드 클릭)에 들어갈 자료를 정리한 문서다.
**누가 만드는지**로 나눴다 — 코드로 만드는 게 나은 것과 사람이 만드는 게 나은 것은
성격이 다르다.

- 🤖 **코드** — 저장소·PDF에서 사실을 뽑아 SVG로 그린다. 데이터가 바뀌면 그림도
  따라온다. `richContent/ArchitectureDiagram.tsx` + `data.ts` 의 `diagrams[]`.
- ✋ **직접** — 툴이나 손으로 만든다. 판단·감각·실물이 필요해서 코드로는 안 나온다.

> 넣는 방법: PNG를 `public/projects/op/` 에 두고 `data.ts` 의 해당 프로젝트
> `gallery` / `heroImage` / `problemShot` 에 경로를 적으면 된다. 최적화(WebP 변환·
> 리사이즈)는 넣기 전에 요청할 것.

## ✋ 직접 만드는 것

### 1. 정식 ERD ⭐⭐⭐

**툴**: dbdiagram.io · ERDCloud · DataGrip · DBeaver (역공학 기능)

코드로 만든 「데이터 도메인 지도」는 **"도메인을 나눠 설계했다"** 를 증명한다.
정식 ERD는 **"데이터 모델링을 할 줄 안다"** 를 증명한다. **둘은 다른 이야기라
둘 다 있는 게 맞다.**

정식 ERD에 있어야 하는 것 (도메인 지도엔 없는 것):

- 컬럼별 **타입**과 길이 (`VARCHAR(500)`, `BIGINT`)
- **PK / FK / UNIQUE / NOT NULL** 표기
- **카디널리티** (크로우풋: 1:N, N:M)
- **인덱스** — PDF 10쪽의 "조회 중심 테이블 인덱스 및 페이지네이션 고려"가
  여기서 증명된다. 지금은 글로만 있다.

대상: **득근득근** (테이블 31개). 전부 그리면 읽히지 않으니 **핵심 12~15개**만.
파싱해 둔 원본이 `docs/muscleup-erd-source.json` 에 있다 — 테이블·컬럼·관계·nullable·length가
전부 들어 있으니 그대로 옮기면 된다.

### 2. Before / After 비교 ⭐⭐⭐ — 가장 강력

**"개선했다"고 쓰는 것과 전후를 나란히 보여주는 건 완전히 다르다.**
PDF 18쪽에 이미 근거가 있다: _"기존 방식의 가독성 문제를 개선하기 위해 표(Table)
구조로 재구성"_, _"실제 사용자 피드백을 반영. 레이아웃·가독성·시각적 위계를 조정"_.

| 대상                       | 찾을 것                                                  |
| -------------------------- | -------------------------------------------------------- |
| 총학생회 **조직도**        | 개편 전 화면                                             |
| 총학생회 **역대 총학생회** | 표로 바꾸기 전 화면                                      |
| **aClub 2025 → 2026**      | 프로젝트장으로 개편한 전후 ← 승진 서사가 여기서 증명된다 |

옛 커밋, 발표 자료, 예전 캡처 폴더에 남아 있을 가능성이 높다.

### 5. 유저 플로우 / 화면 흐름도 ⭐⭐

**툴**: Figma · Whimsical · FigJam

실제 화면 캡처를 이어 붙여 **"탐색 → 상세 → 신청"** 같은 동선을 보여주는 그림.
캡처가 재료라 코드로는 못 만든다. aClub·총학생회처럼 **동선 설계가 핵심 기여인
프로젝트**에 특히 강하다.

### 6. 와이어프레임 / 초기 스케치 ⭐⭐

손으로 그린 것도 좋다. **완성 화면만 있는 포트폴리오는 결과만 보여주고, 스케치가
있으면 사고 과정이 보인다.** "이건 왜 이렇게 배치했나요"에 그림으로 답이 남는다.

### 7. 팀 협업 흔적 ⭐⭐ — 지금 하나도 없다

aClub · 총학생회 · TSEROF · 수어지구가 팀 프로젝트인데 **"3인 팀"이라는 글자 말고는
증거가 없다.** 신입 채용에서 "팀에서 어떻게 일하나"는 기술만큼 본다.

- PR 리뷰 코멘트 (내가 남긴 것 / 받은 것)
- 이슈 트래커 · 스프린트 보드
- 노션 회의록 · 역할 분담표

### 8. 운영 중 겪은 사건 ⭐⭐

PDF 12쪽의 **ACM 리전 함정**(CloudFront는 us-east-1 인증서 필요), **캐시 무효화**
같은 건 실제로 겪은 사람만 아는 이야기다. 그때의 **에러 화면 · 로그 · 모니터링
캡처**가 남아 있으면 강력하다. 장애를 겪고 고친 경험은 신입에게 흔치 않다.

### 9. 게임 프로젝트 도식 ⭐

**툴**: Figma · draw.io

TSEROF · DarkLab · 아주대탐험은 웹 아키텍처 틀이 안 맞는다. 대신:

- **게임 루프** 흐름도 (탐색 → 전투 → 보상 → 성장 → 다음 웨이브)
- **레벨 난이도 곡선** (튜토리얼 → 응용 → 복합)
- **상태 전이도** (Patrol → Chase → Attack)

### 10. 유저테스트 자료 ⭐

TSEROF는 이미 있다(피드백 → 개선 슬라이드, `tserof-feedback.webp`). **다른
프로젝트에도 있으면** 같은 형식으로 넣는다.
