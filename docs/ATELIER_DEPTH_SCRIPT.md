# 의뢰 공방 심화 문답(2층) — 분기 트리 + AI 맞춤 질문 (계획, 2026-08-24)

> **상태: 계획서. 아직 코드 없음.** 확정되면 구현하고, 1층처럼 이 문서는 근거로 남긴다.
> 1층(접수 릴레이 설문)은 [ATELIER_INTAKE_SCRIPT.md](./ATELIER_INTAKE_SCRIPT.md) — 구현 완료.
> 배경은 [COMMISSION_ATELIER.md](./COMMISSION_ATELIER.md), 운영은 [ATELIER_GUIDE.md](./ATELIER_GUIDE.md).

## 0. 한 줄

접수 뒤 `/commission/<token>` 의 심화 문답을 **1층과 같은 NPC 릴레이 설문**으로 바꾸고,
문항을 세 겹으로 쌓는다: **공통 7슬롯(기존) → 사이트 종류별 분기 문항(신규) →
AI 가 그 의뢰만 보고 뽑은 맞춤 질문(신규, 최대 5개)**. 그 뒤는 기존 3층(체리 질문지).

신박한 의뢰(고정 문항이 과녁을 빗나가는 의뢰)일수록 세 번째 겹이 일을 한다 —
사람이 미리 적어 둘 수 없는 질문은 AI 가 뽑되, **몇 개 물을지·언제 묻는지·끝났는지는
전부 규칙이 정한다.**

## 1. 지키는 원칙

| 원칙                                                                                          | 근거                                                                             |
| --------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| **완료(`depth_done`)는 고정 필수 슬롯만 본다.** 분기 문항도 AI 질문도 완료 조건에 안 들어간다 | 체리 질문이 완료 조건 밖인 기존 원칙 그대로 — "기준이 의뢰마다 달라지면 안 된다" |
| **AI 는 질문을 제안만 한다.** 생성은 정해진 시점에 1회, 상한 5개, 저장은 구조화 데이터로      | "결과는 규칙이 정하고 LLM은 대사만"의 질문판                                     |
| **AI 가 죽어도 2층은 완주된다.** 공통 슬롯 + 분기 문항은 선택지 경로라 LLM 0회                | 1층과 같은 보증선                                                                |
| **접수 원문은 건드리지 않는다.** `store_depth_answers` 의 "견적·요약 불변" 규칙 유지          | 관리자가 본 값이 흔들리면 안 된다                                                |
| **연락처는 여전히 track 응답에 없다.** AI 질문 생성 프롬프트에도 연락처를 넣지 않는다         | 링크 전달 경로는 통제 불가                                                       |

## 2. 전체 구조 — 2층의 세 겹 + 기존 3층

```
접수 완료 → /commission/<token>  (릴레이 설문 UI 재사용)
│
├ ① 공통 7슬롯 (기존 _DEPTH_SLOTS, 문구·필드 그대로 — 선택지 카드만 입힘)
│    운영·수정 주체 / 콘텐츠 준비 / 성공 기준 / 기존 자산 / 피할 것 / 참고 이유 / 결정권자
│    → 필수 슬롯이 다 차면 depth_done (지금과 동일)
│
├ ② 종류별 분기 문항 (신규 — site_type 이 고른다, 3~6개)
│    쇼핑몰이면 상품·배송·결제, 예약이면 예약 단위·취소 규정 …
│    답은 requirements["branch"] 에 {문항id: 답} 으로 누적
│
├ ③ AI 맞춤 질문 (신규 — ①·② 가 끝난 시점에 1회 생성, 최대 5개)
│    "이 의뢰를 실제로 만들려 할 때 아직 불명확한 것"을 모델이 뽑는다
│    requirements["ai_questions"] 에 [{id,question,answer}] 로 저장
│
└ ④ 체리 질문지 (기존 pending_questions — 산출물 검토 뒤. 손대지 않는다)
```

담당 NPC 배정(릴레이 연출): **도안**이 ①을, **체리**가 ②의 구조·콘텐츠 문항을,
**굴뚝**이 ②의 결제·로그인·데이터 문항을, **먹지**가 사진·자료 문항을 맡는다.
③은 **그 질문과 가장 가까운 직군**이 묻되, 매핑이 애매하면 도안이 묻는다
(질문 생성 시 모델에게 `speaker` 필드도 같이 받는다 — 틀려도 대사 담당만 바뀔 뿐이라 안전).

## 3. ② 종류별 분기 문항 — 대본

형식: 1층과 같은 선택지 카드. **"직접 적을게요"와 "나중에요"는 전 문항 공통**(생략).
답은 견적을 바꾸지 않는다 — 여기는 "얼마짜리"가 아니라 "어떻게 만드나"의 층이므로
가격 꼬리표도 없다. (예외: 답이 새 기능을 드러내면 — 예: "결제도 필요하네요" — features 에
누적만 하고, 재견적은 관리자 몫이라는 한 줄을 도안이 말한다.)

## 4. ③ AI 맞춤 질문 — 설계

**목적**: 고정 트리가 못 덮는 "신박한" 의뢰에서만 일하는 겹. 전형적 의뢰면 0~2개,
없으면 0개가 정상이다.

- **생성 시점**: ①·② 문항이 모두 끝난(답했거나 건너뛴) 순간, **한 번만**. 도안이
  "잠깐만요, 식구들이 정리한 걸 보고 있어요…"라고 말하는 사이 서버가 생성한다.
- **호출**: `commission_service.generate_ai_questions(commission)` — `json_object` 로
  `{"questions": [{"question": "...", "speaker": "planner|designer|frontend|backend|intake"}]}`.
  프롬프트에 들어가는 것: 접수 요약·requirements 전부·①②의 답·**이미 물은 질문 전체 목록**.
  들어가지 않는 것: 연락처. 지시: "실제로 만들기 시작할 때 막히게 될 불명확한 지점만,
  이미 답이 있는 것과 겹치지 않게, **최대 5개, 명백하면 빈 배열**. 전문용어 금지."
- **후처리(규칙이 통제)**: 5개로 자르고, 기존 질문·답과 문장 중복 제거, 각 질문 120자
  제한, 실패·타임아웃이면 **조용히 0개**(2층은 이미 완주 상태라 잃는 게 없다 — 단
  1층 폴백처럼 로그는 남긴다).
- **저장**: `requirements["ai_questions"] = [{id: "a1", question, answer, speaker}]`.
  `pending_questions`(체리 질문지)와 **분리** — `import_planner_questions()` 가 재발행 때
  목록을 통째로 갈아끼우므로 같은 그릇에 담으면 AI 질문이 증발한다. 답 병합 규칙은
  체리 질문과 동일(빈 답이 기존 답을 덮지 않음, 재생성 시 질문 문장으로 답 이관).
- **묻기**: 릴레이 UI 가 `speaker` 담당 NPC 로 하나씩 묻는다. 전부 자유 입력(선택지 없음 —
  선택지를 만들 만큼 정형이면 애초에 ②에 있어야 한다). 건너뛰기 가능.
- **관리자 화면**: `CommissionWorkboard` 상세에 "AI 가 더 물은 것" 블록 추가(질문+답).
  에이전트 브리프(`workspace` 요구사항 문서)에도 같은 블록이 들어간다 — 여기까지 가야
  체리가 3층에서 같은 걸 또 묻지 않는다.

**안 하는 것**: 답을 듣고 꼬리 질문을 무한히 이어가는 자유 대화형 심문. 생성은 1회다.
더 파고들 게 남았으면 그건 3층(체리)과 사람(재훈)의 몫 — 2층이 취조실이 되지 않게 하는
마지노선이다. (자유 대화창은 1층처럼 항상 열려 있으므로, 손님이 스스로 보태는 길은 있다.)

## 5. UI — 1층 엔진 재사용

- `useIntakeFlow` 를 일반화하지 않고, **대본을 주입받는 형태로 한 단계 추상화**한다:
  `useDialogueFlow(script, {draft, onSlot})`. 1층 대본은 지금 그대로, 2층 대본은
  `atelierDepthScript.ts` 가 **런타임에 생성**한다(공통 7슬롯 + site_type 분기 + AI 질문을
  이어붙인 배열 — AI 질문은 track 응답에 실려 온다).
- `/commission/[token]/page.tsx` 의 `CommissionDesk mode="depth"` 자리에 릴레이 UI 를
  넣되, **기존 자유 채팅(`consult_depth`)은 없애지 않는다** — "직접 말할게요"와 하단
  말 걸기가 그 경로를 그대로 탄다. 지난 문답 복원(`track.messages`)도 유지.
- 진행 표시: 오른쪽 `DepthProgress` 는 유지하되 ②③의 답도 보여준다. 견적 티커는
  2층에 **없다**(위 3장의 이유).
- 시안 미리보기(`PreviewPane`)·planner 질문 흐름은 그대로 위에 얹힌다.

## 6. 구현 순서 (승인 후)

1. 백엔드: `requirements["branch"]`·`["ai_questions"]` 저장 + `store_depth_answers` 확장,
   `generate_ai_questions()` + 폴백, track 응답에 두 목록 노출 — 테스트
   (`test_commission_depth.py` 확장: 저장·병합·재생성 답 보존·상한·중복 제거)
2. `atelierDepthScript.ts` — 공통 7슬롯 카드화 + 종류별 트리(3장 표) + AI 질문 합성
3. `useIntakeFlow` → `useDialogueFlow` 추상화 (1층 회귀 없음을 기존 동작으로 확인)
4. `/commission/[token]` 릴레이 UI 교체, `DepthProgress`·관리자 화면·에이전트 브리프 반영
5. E2E: 쇼핑몰 한 건을 접수→2층 완주→AI 질문 생성→관리자 상세 확인

## 7. 결정 필요 (확정 전)

1. **AI 질문 생성 모델** — 기존 `OPENAI_MODEL` 그대로(제안) vs 저렴한 모델 별도 지정.
   호출은 의뢰당 1회라 비용 차이는 무시할 수준.
2. **① 공통 7슬롯의 선택지화 범위** — 7개 전부 카드 선택지를 다는 대신, 성격상 자유
   입력이 맞는 것(기존 자산·참고 이유)은 자유 입력 유지(제안).
3. **②에서 새 기능이 드러났을 때** — features 누적 + "견적은 담당자가 다시 안내"
   한 줄(제안) vs 그 자리에서 재견적 표시. 제안 쪽이 "접수 원문 불변" 원칙과 맞는다.
