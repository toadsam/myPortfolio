## 1. 배치 오버홀 — 컨셉의 "육각 방위 원반 섬"으로 (3fb47d0)

### 문제
컨셉 아트는 섬마다 미니광장을 중심으로 건물이 **안쪽을 보며 고리**로 서는
배치인데, 기존 마을은 격자 행 배치였다. 건물 회전도 90도 스냅뿐이었다.

### 고민의 핵심 — 호 배치에서 각도 배분의 함정
건물을 고리에 세울 때 각도를 `폭/반지름`으로 나누면 **겹친다.** 안쪽을 보는
건물끼리는 뒤꽁무니가 아니라 **앞모서리**(반지름 ρ−d/2)에서 부딪히기 때문이다.
반지름을 200번 키워도 겹침이 안 풀리던 원인이 이것이었다.

처방은 앞모서리 반지름 기준의 각도 배분:

```
angleOf = 2·asin( (w/2 + GAP/2) / max(0.8, ρ − d/2) )      GAP = 0.7
```

### 증명 (check-village 15종 전부 통과, 실행 출력 그대로)

| 검사 | 수치 |
|---|---|
| 건물 겹침 (OBB SAT) | **0쌍**, 최소 여유 0.85 |
| 건물이 해자(a=42, b=38) 안 | **27채 모두** (작업 전엔 9채 침범, 최악 1.17배 이탈) |
| 구역 섬이 같은 고리에서 시작 | 6구역 모두 물가 반지름 **13.2** (DISTRICT_INNER) |
| 구역 단 사이 골짜기 | 마주보는 구역 모두 **1 이상** (최소 1.94) |
| 해자 ⊂ 잔디 원반(r=53) | 해자 바깥끝 45.1, 여유 **7.9** |
| 이웃 구역 다리 | 6쌍 모두, 물 위 다리 12개 |

걷기 검증(BFS, 격자 표본):

- 섬 밖 탈출 불가 — 껍질 밖 표본 **5,407점 전부 막힘**
- 갇히지 않음 — 설 수 있는 땅의 **93%** 도달 가능 (원반의 44%가 땅, 41%가 활동 범위)
- 걸어서 건물 앞까지 — **26채 전부** (project-mystock 회귀도 해소)

## 2. 섬 테두리 울타리 — "유령 담장" 버그 (e300483, 6a80463, 8dafb12)

### 문제
섬 테두리에 울타리를 둘렀는데 스크린샷에는 **구멍이 숭숭** 났다. 생성 로그는
"143토막 설치"라는데 화면에는 거의 없었다.

### 진단 — 로그가 거짓말을 한 이유 (버그 2겹)
1. `place()`의 물가(nearShore) 판정이 낮은 담장을 **조용히 거부**하는데, 로그는
   거부 전 시도 횟수를 세고 있었다. 실제 설치는 **0토막에 가까웠다.**
2. 거부된 담장도 `walls[]` 배열에는 들어가서, 빈자리를 메우는 울타리 필러가
   "이미 담장 있음"으로 건너뛰었다 — **유령 담장**이 자리를 차지한 것.

같은 병이 차선 등불에도 있었다: 시도 25개 중 실제 설치 **14개**(11개 무음 탈락).

### 처방·증명
- 성공 반환값을 확인한 뒤에만 세고, 배열에도 성공한 것만 넣는다.
- 대문 판정을 "길 근처(onRoad, 오차 1.37)"에서 **스포크 칸(s:1 마킹) 기준**으로
  바꿔, 182개 슬롯 전부가 대문으로 오판되던 것을 해소. 디딤돌도 84→26개로
  (오판이 낳던 222k 삼각형 낭비 제거).
- 장식물 삼각형 예산: 한때 1,825k로 상한(1,800k) 초과 → 구역당 집 수를
  9/8/8/7/7/6으로 조정해 **1,722k / 1,800k** (여유 78k).

## 3. 물 품질 — "뜨개질 격자"의 수학 (ae13359, ed9e52b)

### 문제
부감에서 물이 물결이 아니라 **짜인 그물/격자 무늬**로 보였다. 석호에서 잡았더니
바깥 해자·개울 리본에서 같은 병이 재발했다.

### 진단 — 타일 반복 횟수가 무늬를 만든다
물결 타일 한 칸의 월드 크기 = `1 / (UV_PER_UNIT × scale)`. 잔결 배율 8이면
타일 0.25유닛:

| 수면 | 폭 | 0.25유닛 타일 반복 | 결과 |
|---|---|---|---|
| 개울 | 1~1.9 | 4~8번 | 물살로 보임 |
| 해자 | 2.2 | 9번 | 경계선 |
| 석호 | ~20 | **80번** | 격자 무늬로 읽힘 |

눈이 되풀이를 알아채는 순간 물결은 무늬가 된다.

### 처방 — 세 번째 "큰 너울" 법선 층 (waterFlow scaleC/bigWeight)
반복 주기를 깨는 성긴 층을 수면마다 **폭에 맞춰** 얹었다:

| 수면 | scaleC | 너울 타일 크기 | 근거 |
|---|---|---|---|
| 석호 | 0.21 | ≈9유닛 | 폭 20에 두어 번 |
| 바다 | 11 | (96배율 잔결의 주기를 깸) | 스파클 타일 반복 제거 |
| 해자·개울 리본 | 0.9 | 2.2유닛 | **리본 폭에 정확히 한 번** |

부수 조치의 수치 근거:
- 깊이 색: `smoothstep(물가거리/4.5)`는 폭 2.4짜리 물을 통째로 "얕음" 판으로
  만든다 → 지수 램프 `1−exp(−(sd·wob)/1.35)` + 노이즈 얼룩(wob 0.7~1.3).
- 밤 물비침(WaterGlints): 등불당 **삼각형 2개**짜리 가산 타원. 세기는 팔레트
  `lamp` 연동 `clamp((lamp−0.85)/1.6)` — 한낮 0, 진짜 평면 반사(비쌈) 없이
  밤 수면을 채운다.
- 닫힌 고리(해자)의 UV는 총 v를 정수로 맞춘다 — 안 맞추면 둘레 155유닛의
  소수부만큼 북쪽 꼭짓점에 물결 끊김 선이 생긴다. 잔결 배율 8:5가 정수이고
  서로 배수가 아닌 것도 같은 이유(고정 간섭무늬 방지).

## 4. 로딩 최적화 — 54.0 → 30.3MB (72d82e4)

### 문제
첫 접속에서 빈 하늘만 보였다. 두 원인: 다운로드가 무겁고, 로딩 중 보여줄 게
없었다.

### 진단 — 무게의 실체를 쟀다
- 서빙 GLB 합계 **54.0MB**, 그중 **약 8할이 내장 JPEG 텍스처.**
  건물 한 채 예: 900KB = baseColor 1024² JPEG 536KB + normal 512² 279KB + MR 95KB.
  지오메트리는 이미 Draco 압축이라 더 줄일 게 없었다.
- `raw/` 폴더 2.2GB는 서빙되지 않는다 — du로 잴 때의 함정.

### 처방 — GLB 컨테이너 수술 (scripts/compress-glb-webp.mjs)
sharp/libvips가 이 환경에서 깨져 있어(`colourspace: parameter space not set`)
gltf-transform을 못 쓴다. GLB를 직접 열어 **이미지 bufferView만** Pillow로
WebP 변환(노멀 q92, 그 외 q85), BIN 재조립, `EXT_texture_webp` 선언.
지오메트리는 1바이트도 안 건드린다. 변환 결과가 원본의 0.97배보다 크면 원본 유지.

### 증명
- 다운로드: **54.0 → 30.3MB** (−44%). 현재 서빙 폴더 실측 30.7MB.
- 화질: 헤드리스 캡처 A/B 비교로 화면 차이 없음 확인 (three GLTFLoader가
  EXT_texture_webp 정식 지원).
- 체감: 40Mbps 스로틀(CDP 에뮬레이션)로 로딩 베일("마을을 짓는 중… n%") →
  마을 완성 → 인트로 순서 검증. 베일에는 25초 안전장치(에셋 404 대비).
- 한계 명시: VRAM 283MB는 그대로다 — WebP는 디코드 후 동일. VRAM은 KTX2가
  다음 카드.

## 5. 물길 교차점의 X자 막대·파편·검은 다각형 (1fce97c)

### 문제 (사용자 스크린샷 3종)
1. 해자×개울 교차점에서 **검은 막대가 물 위를 X자로** 가로지름
2. 물길 끝 잔디 위에 **연한 사각 조각**
3. 밤바다에 **거대한 검은 다각형**(지느러미)

### 진단 — 소거법으로 범인을 특정했다
- ①: 개울은 해자를 **가로질러** 폭포로 나간다. 도랑 둑(WaterBanks)은 열린
  물길의 "끝 어귀 2.2유닛"만 깊이를 눕혔으므로, 교차점 한복판에서는 해자 둑이
  개울 물 위를(닫힌 고리는 depth가 항상 1), 개울 둑이 해자 물 위를 최대 깊이로
  팠다.
- ②: 두 겹 — (a) 생성기가 개울 끝을 해자 중심선에 밀어 넣지만 해자 굽이
  (drift ±1.9)가 각도에 따라 물길을 관통시켜 반대편 잔디에 얹혔고, (b) 둑
  깊이만 0으로 눕히면 어깨 돌출(out 0.6)이 **물 높이의 팬케이크**로 남는다.
- ③: 헤드리스 씬 프로브로 소거 — 인스턴스 메시(임포스터 나무) 전부를 꺼도
  남았고, **1,536 삼각형짜리 IslandCliff**(절벽: 6링×128세그먼트×2)를 끄니
  사라졌다. 달빛을 등진 곶이 빛을 0 받아 완전 검정 실루엣 = 종잇장 다각형.

### 처방 — 전부 런타임, 데이터 무변경
- 마디마다 **다른 물줄기 수면까지의 거리**를 재서 1.2유닛 안이면 둑을 눕힘
  (1.2 = 둑 어깨가 상대 수면을 밟지 않는 최소 여유)
- 어깨도 깊이 k와 함께 접음: `h + out·k` → 눕힌 단면이 수면 폭 안, 수면 3cm 아래로 숨음
- 개울 끝 트림: 끝 4유닛 안에서 "다른 물 속(여유 0.2)" 마디를 찾으면 거기서 자름
  — 폭포로 가는 끝은 근처에 다른 물이 없어 **안 잘린다** (조건이 스스로 지켜줌)
- 절벽: `emissive #2e3c55 × 0.42 × GLINT_STRENGTH` — 등불 세기 연동이라
  **밤에만 켜지고 한낮에는 정확히 0** (낮 절벽 색 무손상, 캡처로 확인)

### 증명
- 수정 전후 동일 카메라 캡처: X자 막대·사각 stub·파편 소멸, 교차점이 자연스러운
  합류부. 밤 곶은 검은 다각형 → 은은한 달빛 바위.
- `check:village` 15종 그대로 전부 통과 (물길이 해자까지: 6줄기, 잔여 −0.4).
- `tsc --noEmit` 통과. 걷기·배치 데이터는 안 건드림(렌더 전용 수정).

## 6. 검증 방법론 — 이 수치들을 어떻게 얻었나

- **정합성**: `scripts/check-village.mjs` 15종 (OBB SAT 겹침, 해자 포함,
  BFS 도달성, 탈출 불가 등). 모든 배치 커밋은 이 15종 통과가 전제.
- **시각**: Playwright 헤드리스(channel: chromium) + `__THREE_DEVTOOLS__` 훅으로
  renderer를 잡아 카메라를 못 박고 캡처. R3F v9는 `canvas.__r3f`를 안 남긴다.
  함정: 마지막 렌더 패스는 후처리 합성 쿼드 씬(삼각형 1)이라, 씬/카메라 저장은
  `camera.isPerspectiveCamera`일 때만 해야 한다.
- **범인 특정**: 부류별 `visible=false` 소거법 + 픽셀 → 월드 역투영 →
  바운딩박스 교차 조회. "검은 다각형=절벽"은 이 방법으로 특정했다.
- **움직임**: 카메라 고정 + 대상 외 메시 전부 숨김 + 1초 간격 스크린샷 해시 비교.
