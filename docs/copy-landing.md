## 🏋️ 득근득근 (MuscleUp)

> GAMIFIED FITNESS · 3-TIER FULL-STACK

**TL;DR**

|         |                                                               |
| ------- | ------------------------------------------------------------- |
| 무엇을  | 운동 기록을 게임처럼 지속하게 만드는 피트니스 커뮤니티 플랫폼 |
| 왜      | 운동 앱은 기록은 되지만 '다시 오게' 만드는 장치가 약함        |
| 결과    | REST 백엔드 + Socket.IO 실시간 서버를 분리한 3-tier 구조      |
| 내 역할 | 1인 풀스택 — 기획·프론트·백엔드·실시간 서버                   |

**메타**

- **팀:** 개인 프로젝트 (풀스택 1인)
- **역할:** 핵심 루프 설계 · 프론트 · 백엔드 · 실시간 서버
- **스택:** React 19 · TS · TanStack Query · Spring Boot 3.5 · Socket.IO · JWT/OAuth · S3
- **실행:** 3-tier(FE:5173 · BE:8080 · Realtime:4001)
- **저장소:** https://github.com/toadsam/Ajou_MuscleUp

**문제**
운동 앱은 기록하는 순간엔 유용하지만 꾸준히 돌아오게 만드는 장치가 약하다. 기록이 캐릭터 성장·랭킹·실시간 커뮤니티로 즉시 연결되는 경험이 필요했고, 자주 바뀌는 실시간 상태를 REST와 분리해야 했다.

**가설**
"운동 기록을 캐릭터 성장·랭킹·라운지로 즉시 연결하고, 빈번히 바뀌는 실시간 상태(위치·채팅·이모트)는 Socket.IO 서버로 분리하면 — 사용자가 '다시 오는' 이유가 생기면서 서버도 감당 가능하다."

**아키텍처**

- **View** — React 19 + TanStack Query: 홈·라운지·랭킹·AI (PWA)
- **API** — Spring Boot 3.5: 16 도메인 · JWT/OAuth · S3 · PDFBox
- **Realtime** — Node + Socket.IO: 라운지 위치·채팅·이모트 (:4001)
- **DB** — MySQL / PostgreSQL: 유저·기록·크루·이벤트

**기술 의사결정**

| 영역     | 선택                       | 이유 / 대안                                                 |
| -------- | -------------------------- | ----------------------------------------------------------- |
| 실시간   | Socket.IO 분리 서버        | 빈번한 상태(위치·채팅)를 REST와 분리 ↔ REST 폴링(부하·지연) |
| 인증     | JWT access/refresh + OAuth | 무상태·간편 로그인·쿠키/Bearer 겸용 ↔ 자체 세션(스케일↓)    |
| 서버상태 | TanStack Query             | 캐시·재검증으로 서버 상태 일원화 ↔ 수동 fetch(중복 상태)    |
| 파일     | 로컬/S3 추상화             | 개발은 로컬, 배포는 S3로 전환 ↔ S3 고정(로컬 불편)          |

**핵심 코드**

```ts
// server.ts (realtime) — 라운지 상태는 Socket.IO 서버가 전담, REST와 분리
io.on("connection", socket => {
  socket.on("move", p => room.update(socket.id, p)); // 위치
  socket.on("chat", m => io.to(room.id).emit("chat", m));
  socket.on("disconnect", () => room.leave(socket.id));
});
```

```ts
// axios-interceptor.ts — 401이면 refresh로 토큰 갱신 후 재요청
api.interceptors.response.use(ok, async err => {
  if (err.response?.status === 401) {
    await api.post("/api/auth/refresh"); // access 재발급
    return api(err.config); // 원요청 재시도
  }
  throw err;
});
```

**트러블슈팅**

- **Refresh Token Rotation의 경쟁 조건을 줄이기 위해 기존 토큰을 유지했습니다** — 같은 refresh 토큰을 가진 두 재발급 요청에서, A가 토큰 값을 바꿔 저장한 뒤 B가 이전 값으로 조회하면 B가 실패할 수 있었습니다. 모든 동시 요청에서 반드시 발생하는 것은 아니며 처리 순서에 따른 문제였습니다. → 72b38fa → bacef85에서 새 refresh 토큰 생성·기존 레코드 갱신을 제거하고 검증한 기존 토큰을 반환했습니다. 클라이언트의 single-flight(refreshing 플래그와 대기 큐)는 이미 있던 장치로, 같은 페이지에서 재발급 요청을 묶는 역할입니다. 서버 수정과 동시에 새로 도입한 것으로 설명하지 않습니다. 이후 64e41f2에는 로테이션과 유예 처리가 다시 추가됐습니다. 토큰 유지 방식과 후속 로테이션 방식을 시점별로 구분합니다.
  - 근거: 수정 전후 확인. 서버 토큰 유지 변경과 기존 single-flight를 분리했습니다. 후속 로테이션 도입을 현재 코드와 혼동하지 않습니다. [확인한 코드](https://github.com/toadsam/Ajou_MuscleUp/commit/bacef85146739a5c915177fe12c4e0be26bfe7d2)
- **인덱스를 넣고 재 보니, count 쿼리가 남은 병목이었습니다** — 아래 목록 네 곳이 모두 정렬 페이지네이션인데 정렬·필터 컬럼에 인덱스가 없었습니다. 회원 50명이라 화면에서는 문제가 없습니다. 데이터가 늘어날 때의 응답 시간을 확인하고자 했습니다. → 정렬이 사라지고 인덱스를 거꾸로 훑는 계획으로 바뀝니다. 목록 네 개가 668~2472배. 합성 데이터 20만 행·7회 중앙값으로 목록 SQL과 count SQL의 합산 시간을 확인했습니다. 이는 HTTP 요청 전체의 응답 시간이 아닙니다.
