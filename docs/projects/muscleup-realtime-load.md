# 득근득근 실시간 서버 부하 측정 (2026-08-31)

## 왜 쟀나

상세 페이지의 가설은 **두 문장**이다.

> "운동 기록을 캐릭터 성장·랭킹·라운지로 즉시 연결하고, 빈번히 바뀌는 실시간
> 상태(위치·채팅·이모트)는 Socket.IO 서버로 분리하면 — 사용자가 '다시 오는'
> 이유가 생기면서 **서버도 감당 가능하다**."

앞 절반(다시 온다)은 [`muscleup-impact.sql`](./muscleup-impact.sql) 로 잰다.
뒤 절반은 **한 번도 재지 않았다.** 인덱스는 표당 20만 행까지 재 놓고, 정작 이
프로젝트를 대표하는 아키텍처 결정은 안 잰 상태였다.

## 재는 대상의 실제 동작

`realtime/src/server.ts` 를 읽고 확인한 것:

- `player:move` 는 **즉시 브로드캐스트하지 않는다.** `pendingBroadcast` 플래그만
  세우고 `setInterval(…, 60)` 이 한 번만 내보낸다(최대 16.7Hz). 이동 트래픽이
  이동 횟수와 무관해진다 — **잘한 결정이다.**
- 다만 매 틱마다 `listPlayers()` **전원 목록 전체**를 전원에게 보낸다.
  `PlayerState` 는 `growthParams`(숫자 19개)까지 안고 있어 한 명이 무겁다.
- 왕복 시간은 서버가 이미 갖고 있는 `ping:check` → `ping:result` 로 잰다.
  앱 자신의 프로토콜이라 별도 계측을 안 붙여도 된다.

## 방법

- 실제 `realtime/src` 를 그대로 띄운다(`tsx src/server.ts`, PORT=4001).
- 클라이언트는 `socket.io-client` 로 `lounge:join` → 초당 10회 `player:move`,
  초당 1회 `ping:check`. `growthParams` 를 실제와 같이 채운다 — 빼면
  브로드캐스트 크기가 절반도 안 돼 측정이 거짓이 된다.
- 단계마다 **서버를 새로 띄우고 16초씩 3회**, 중앙값.
- 서버 CPU 는 `tsx` 래퍼가 아니라 **포트를 실제로 쥔 프로세스**를 잰다.

### ⚠️ 처음 잰 값은 틀렸다 — 하네스를 재고 있었다

처음엔 한 프로세스에 소켓을 다 물렸다. 결과는 "100명에서 p95 244ms, 150명에서
2.3초" 였다. 그대로 실었으면 **서버를 5배 억울하게 만들 뻔했다.**

이상하다고 본 근거는 CPU 였다. **서버 CPU 가 한 코어의 20% 를 넘은 적이 없는데**
왕복이 2초까지 뛰었다. Node 는 단일 스레드다 — 서버가 병목이면 한 코어를 100%
물고 있어야 한다. 즉 그때 막힌 건 서버가 아니라 하네스였다. 클라이언트도 서버와
똑같이 N² 만큼 JSON 을 파싱하는데 그걸 스레드 하나로 하고 있었다.

**워커 프로세스당 소켓 25개로 쪼개니** 같은 100명에서 p95 가 244ms → **50ms** 로
내려갔다. 아래 표는 쪼갠 뒤의 값이다.

## 결과 (16초 × 3회 중앙값)

| 동시접속 | p50 | p95 | p99 | 브로드캐스트/s | 서버 송신 | 1인 수신 | 서버 CPU | RSS |
| -------: | --: | --: | --: | -------------: | --------: | -------: | -------: | ---: |
|       25 |  2ms |  7ms |  11ms | 15.2 | 5.6 MB/s | 229 KB/s |  4.3% | 121MB |
|       50 |  4ms | 26ms |  30ms | 15.7 | 23.0 MB/s | 472 KB/s | 15.2% | 116MB |
|      100 | 22ms | 50ms |  55ms | 15.9 | 93.4 MB/s | 957 KB/s |   34% | 116MB |
|      150 | 104ms | 416ms | 590ms | 14.2 | 187.6 MB/s | 1,280 KB/s | 47.3% | 128MB |
|      200 | 196ms | 3,725ms | 6,527ms | 11.5 | 248.3 MB/s | 1,271 KB/s | 30.1% | 150MB |
|      300 | 185ms | 8,888ms | 11,606ms | 6.2 | 286.0 MB/s | 976 KB/s | 20.7% | 183MB |

## 읽는 법

**1. 100명까지는 문제가 없다.** p95 50ms 이고, 설계한 60ms 주기(16.7Hz)가
15.9Hz 로 거의 그대로 유지된다. 지금 회원이 약 50명이니 **전원이 동시에 라운지에
들어와도 여유가 두 배** 있다. 가설의 뒤 절반은 참이다.

**2. 150에서 꺾이고 200부터 무너진다.** p95 가 50ms → 416ms → 3.7초.

**3. 무너질 때 CPU 는 오히려 내려간다** (47.3% → 30.1% → 20.7%). CPU 를 다 쓰고
막히는 게 아니라, **못 보내서** 노는 것이다. RSS 는 계속 오른다(116 → 183MB) —
못 보낸 것이 큐에 쌓인다는 증거다. 병목은 연산이 아니라 송신이다.

**4. 원인은 구조이고 예측 가능하다.** 매 틱 전원에게 전원 목록을 보내므로
바이트가 **N² 로 큰다.** 실측이 정확히 그렇다:

```
25명   5.6 MB/s
50명  23.0 MB/s   (인원 2배 → 4.1배)
100명 93.4 MB/s   (인원 2배 → 4.1배)
```

플레이어 한 명이 약 **600B** 다(세 지점에서 604 · 601 · 616B 로 일치).
`growthParams` 숫자 19개가 그 대부분이다.

**5. 그런데 진짜 한계는 서버가 아니다.** 100명일 때 **한 사람이 초당 957KB** 를
받는다. 이건 루프백이라 여기선 안 보이지만, LTE 로 접속한 사용자에게는 서버가
버티는 것과 무관하게 **이쪽이 먼저 죽는다.**

## 그래서 다음에 할 것

인덱스 때와 같은 모양이다 — 눈에 띄는 것(이동 폭주)은 60ms 합치기로 이미
해결됐고, 다음 병목은 **거기가 아니라 페이로드**에 있다.

1. **뷰포트 컬링** — 화면에 보이는 사람만 보낸다. N² 를 N×k 로 낮춘다.
2. **델타 전송** — 바뀐 필드만. `growthParams` 는 접속 중에 거의 안 바뀌는데
   초당 16번 다시 보내고 있다. 입장 때 한 번만 보내면 한 명당 600B 가
   수십 B 로 떨어진다.
3. 그다음이 다중 인스턴스 + Redis 어댑터다. **1·2 를 안 하고 3 부터 가면
   서버만 늘리고 대역폭은 그대로다.**

## 조건 (그대로 밝힌다)

- **한 대에서 잰 값이다.** 서버와 클라이언트가 같은 기기(논리 코어 22개),
  루프백이라 실제 네트워크 지연·손실이 없다. 실제 배포에서는 더 나쁘다.
- 클라이언트는 사람이 아니라 스크립트다. 초당 10회 이동은 계속 걷는 상태를
  가정한 것으로, 실제 사용자보다 공격적이다.
- 인증을 안 붙였다. 서버 자체가 `lounge:join` 에서 JWT 검증을 아직 안 한다
  (`// TODO: Verify JWT/access token in realtime server (MVP skips).`).
