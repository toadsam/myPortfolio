## 0. 한 줄

지금의 "도안과 자유 채팅" 접수를 **게임 NPC 대화 형식의 설문**으로 바꾼다.
공방 식구 4명이 **자기 전문 분야만 차례로** 묻고, 선택지마다 **예시와 가격 가산치**가 붙으며,
언제든 그 NPC에게 **자유롭게 말을 걸 수** 있다. 2D 데스크와 3D 공방이 **같은 대본 파일**을 쓴다.

겉은 RPG 대사창 / 속은 설문 + 실시간 참고 견적 / 밑은 기존 `CommissionDraft`·`_baseline_estimate()` 그대로.

## 1. 지키는 원칙 (기존 설계에서 안 바뀌는 것)

| 원칙                                                                                                                            | 근거                                                              |
| ------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| **1층(접수)은 10문항으로 고정, 가볍게.** 목적은 "참고 견적 + 접수번호"까지                                                      | `CommissionDraft` docstring — 문턱을 올리지 말고 뽑는 시점을 뒤로 |
| **제작 슬롯(②)은 1층에서 먼저 묻지 않는다.** 2층(`/commission/<token>`)에서 같은 릴레이 UI로                                    | `_DEPTH_SLOTS` 단일 출처, `test_commission_depth.py`              |
| **금액은 규칙이 정한다.** 선택지 가산치는 백엔드 표의 미러. 최종 금액은 여전히 서버 `_clamp_estimate()` + `ESTIMATE_DISCLAIMER` | 견적 분쟁 방지                                                    |
| **AI 없어도 접수된다.** 선택지 흐름은 LLM 0회 호출로 완주 가능. 자유 대화만 LLM                                                 | "AI가 죽어도 접수는 살아야 한다"                                  |
| **허니팟·레이트리밋·동의는 그대로.** 마지막 접수 폼은 건드리지 않는다                                                           | 유일한 공개 쓰기 경로                                             |

## 2. 흐름

```
도안 (접수)     Q1 어떤 사이트  · Q2 페이지 규모                 ─ 견적 기준선이 정해진다
   ↓ "기획은 체리가 봐 드릴게요"
체리 (기획)     Q3 사이트의 목적 · Q4 꼭 필요한 기능(복수)         ─ 기능 가산치
   ↓ "분위기는 먹지한테"
먹지 (디자인)   Q5 분위기·톤   · Q6 움직임 정도(프리뷰)            ─ 연출 가산치
   ↓ "화면은 리코가"
리코 (프론트)   Q7 참고 사이트 · Q8 모바일 비중  (+ 굴뚝 난입: 로그인/결제 있으면 한마디)
   ↓ "그럼 다시 접수대로"
도안 (접수)     Q9 예산대     · Q10 일정                         ─ 예산 vs 견적 충돌 시 조정 제안
   ↓
도안: 요약 낭독 → "빠진 거 있으세요?" (자유 입력 1회, 건너뛰기 가능) → 견적 카드 → 접수 폼
```

- 각 문항 화면: NPC 대사(타자 연출) → 대사 선택지 카드 → 고르면 **내 대사가 찍히고** NPC **반응 대사** → 다음.
- 모든 문항에 **"직접 말할게요"** 선택지. 누르면 자유 입력 → 기존 `consult`가 슬롯 추출 → 같은 반응 흐름.
- 자유 대화창은 항상 열려 있다(선택지와 별개). 지금 말하는 NPC 페르소나로 답하고, 답 안에 슬롯이 들리면 담는다(묻지는 않는다).
- 진행 중 상단에 **누적 참고 견적**이 산다. 선택지마다 `+n만 원 정도`가 붙고, 고르면 숫자가 굴러간다.
- 건너뛰기 가능: Q1·Q2만 필수(= 현재 `ready_to_submit` 조건 그대로). 나머지는 "나중에요"로 넘길 수 있다.

## 3. 대본 — 1층 10문항

표기: **[슬롯]** = 채우는 `CommissionDraft` 필드, **(+금액)** = `_FEATURE_WEIGHTS`/`_BASE_BY_TYPE` 기준 가산 하한~상한, **예시** = 카드에 보여줄 것.

### 도안 — 접수대 (복귀)

**입장**

> 다시 오셨네요. 식구들 얘기 다 모았어요. 지금까지 고르신 걸로 참고 견적이 **{estimate_min}~{estimate_max}만 원, {weeks_min}~{weeks_max}주** 정도로 나와요. 마지막 두 가지만요.

**Q9. 생각하시는 예산대가 있으세요?** [budget_hint] · 선택

| 선택지                                                                                           |
| ------------------------------------------------------------------------------------------------ |
| "100만 원 아래" · "100~300만" · "300~600만" · "600만 이상" · "아직 모르겠어요" · "직접 적을게요" |

반응 규칙 (핵심):

- 예산 상한 < estimate_min → "솔직히 말씀드리면 지금 고르신 대로면 조금 넘어요. 그런데 방법이 있어요 — {가장 비싼 기능 하나}를 2차로 미루면 {재계산값} 정도로 들어와요. 접수하시고 체리랑 순서를 정하면 돼요." **(견적 숫자가 실제로 다시 굴러가는 걸 보여준다. 선택은 강요하지 않고 기록만)**
- 예산 하한 > estimate_max → "여유가 있으시네요. 그렇다고 비싸게 부르진 않아요(웃음). 대신 연출이나 관리자 화면 같은 걸 넣을 여지가 있다고 적어 둘게요."
- 범위 안 → "딱 맞네요."

**Q10. 언제까지 필요하세요?** [deadline_hint] · 선택

| 선택지                                                                              |
| ----------------------------------------------------------------------------------- |
| "급해요, 한 달 안에" · "두세 달 안에" · "여유 있어요" · "날짜가 있어요 (직접 적기)" |

반응: 예상 주 수와 비교해 "급해요"인데 weeks_min이 넘으면 "그 기간이면 범위를 줄여야 해요. 접수는 되고, 뭘 먼저 할지 체리가 연락드릴 거예요."

**마무리**

> 정리해 드릴게요. (요약 낭독: 유형·페이지·기능·분위기·움직임·기기·예산·일정)
> 빠진 거나 덧붙일 말 있으세요? 없으면 바로 접수할게요.
> → 자유 입력 1회 (건너뛰기 가능) → 견적 카드(`ESTIMATE_DISCLAIMER` 포함) → 기존 접수 폼(이름·이메일·연락처·동의·허니팟)
> → "접수되었습니다. 접수번호 {public_id}. 식구들이 몇 가지 더 여쭤볼 게 있어서, 이 링크로 다시 오시면 이어서 얘기해요." (= 2층 진입 안내)

## 4. 실시간 견적 — 프론트 규칙

- 백엔드 `_BASE_BY_TYPE`·`_FEATURE_WEIGHTS`·페이지 가산 공식을 **`GET /commission/pricing`** 으로 내려 받아 프론트가 같은 계산을 한다 (표를 두 벌 손으로 복사하지 않는다).
- 화면 숫자는 "참고"이며, 매 문항 뒤 서버 `consult`(또는 새 `POST /commission/estimate`, LLM 없이 `_clamp_estimate` 만)로 **서버값으로 덮어쓴다**. 차이가 나면 서버값이 이긴다.
- **신설 가산치** (`_FEATURE_WEIGHTS` 추가): `스크롤연출 (300_000, 800_000, 1)`, `인터랙티브 (1_500_000, 4_000_000, 2)`. 기존 테스트 `test_commission_service.py` 기대값에 영향 없음(새 키워드라).
- 숫자 연출: 굴러가는 카운터, 오를 땐 주황·내릴 땐 초록. 예산 초과 시 도안 반응이 **실제 재계산**을 보여줘야 한다(가장 비싼 기능 제외 → 재계산 → 다시 포함).

## 5. 자유 대화 — 백엔드 변경 최소안

- `POST /commission/consult` 에 `speaker: "intake"|"planner"|"designer"|"frontend"|"backend"` 추가 (기본 intake, 하위 호환).
- `commission_service.consult()` 가 speaker 에 따라 `catalog.py` 의 해당 공방 프로필 말투를 시스템 프롬프트에 섞는다. 슬롯 추출 JSON 형식은 동일.
- 2~4번 NPC 페르소나 프롬프트에 "**먼저 묻지 말 것** — 들리면 담기만" 지시 유지(제작 슬롯 보호).
- fallback(AI 없음)은 speaker 별 고정 대사 3~4개만 추가.

```
src/data/atelierIntakeScript.ts     ← 대본 단일 출처 (문항·선택지·슬롯 매핑·가산 키워드·대사·예시 종류)

  EstimateTicker.tsx                ← 누적 견적 카운터
```

- **2D** `CommissionDesk.tsx`: 채팅창 위에 `IntakeDialogue`를 얹고 speaker 초상화 전환. 설문 끝나면 기존 견적 카드·접수 폼으로 합류.
- **3D** `AtelierInterior.tsx`: 같은 `useIntakeFlow` 를 구독해 speaker 변경 시 카메라를 `atelierRoster` 좌석으로 이동, 해당 NPC 머리 위 말풍선·`IntakeDialogue` 하단 HUD. 난입 대사는 해당 NPC가 잠깐 고개를 드는 애니메이션.
- 예시 미리보기는 **전부 코드(CSS/SVG)** 로 그린다 — 이미지 에셋 없음, 3D GLB 없음(`/atelier` 독립성 유지).
- 모바일: 2D 데스크만. 선택지는 세로 리스트, 예시 카드는 접었다 펼침.

## 7. 2층(심화 문답) — 개요만, 별도 계획

1층 릴레이 UI를 그대로 재사용하되 문항이 **site_type 별로 분기**한다. `_DEPTH_SLOTS` 7개 + 유형별 추가:

| 유형       | 추가로 묻는 것(예)                                        |
| ---------- | --------------------------------------------------------- |
| 예약       | 예약 단위(날짜/시간), 동시 예약 수, 취소 규정, 알림 방식  |
| 쇼핑몰     | 상품 수, 옵션(사이즈·색), 배송·반품, 결제 수단, 재고 관리 |
| 웹서비스   | 회원 종류, 핵심 화면 3개, 데이터 민감도, 외부 연동        |
| 기업소개   | 사업 소개 분량, 연혁·팀, 채용 여부, 뉴스/공지             |
| 포트폴리오 | 작업물 수·종류, 카테고리, 업데이트 빈도                   |

여기서는 NPC가 **되묻는** 비중이 커진다(선택 → 후속 질문). 체리의 `pending_questions`(3층)가 그 뒤에 이어진다.

밟은 함정:

- **선택지 exit 애니메이션을 쓰지 않는다.** 숨은 탭(브라우저 패널 비표시)에서 RAF 가 멈추면 framer-motion exit 이 끝나지 않아
  답한 뒤에도 선택지가 남는다. 사라지는 건 즉시, 나타날 때만 애니메이션.
- **3D 에서 모달은 안 된다.** 검은 배경이 방을 덮어 카메라 이동이 안 보인다. 그래서 HUD 가 따로 있고, HUD 는 화면 아래
  48vh 까지만 차지하며 카메라는 식구가 **위쪽 1/3** 에 오도록 발밑보다 낮은 점(y=-0.05)을 겨눈다.
- 말하는 인형의 들림·발광은 `speaking` 으로, "의뢰 접수하기 →" 라벨은 진짜 호버(`hoveredRaw`)로만 — 섞으면 설문 내내
  접수 안내가 떠 있다.
- 2D 데스크 검증은 인앱 브라우저 패널(모바일 뷰포트)로, 3D 는 Playwright `channel:"chromium"` 으로 했다(숨은 패널에선
  캔버스가 300×150 에 굳어 클릭 판정이 안 된다 — 메모리 `village-headless-capture` 그대로).

## 9. 결정 필요 (계획 확정 전)

1. **Q3(목적)을 1층에 둘지** — `success_metric`(2층 슬롯)과 겹친다. 제안: 1층엔 두되 2층에서 "아까 문의가 늘길 바라셨죠, 구체적으로…"로 **이어 묻는다**. 중복 아님.
2. **굴뚝의 1층 등장 방식** — 난입 한 줄(제안) vs 정식 차례. 제안대로면 굴뚝은 2층에서 결제·회원 문항을 정식으로 맡는다.
3. **"직접 말할게요" 뒤 LLM 슬롯 추출 실패 시** — 그 문항은 `summary`에 원문만 붙이고 넘어간다(제안). 되묻지 않는다.
