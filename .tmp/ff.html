02 · SSE

새로고침을누를사람이없습니다

평가 지표를 둘 다 본 이유 — 혼잡도 예측은 다중 클래스 분류이고, 운영상 BUSY / VERY_BUSY 를 놓치지 않는 게 중요하므로 전체 정확도(Accuracy)와 클래스 균형 성능(Macro F1)을 함께 평가했습니다.

왜 RandomForest 를 운영 모델로 선택했는가
1성능 차이가 작다

Accuracy 0.7984 vs 0.8143 / Macro F1 0.79 vs 0.81. XGBoost 가 더 높지만 운영 모델을 바꿀 정도로 큰 차이는 아님

2운영 안정성이 중요하다

실시간 예측 서비스를 목표로 하므로 최고 성능 1개보다 안정적으로 추론되고 관리되는 모델이 필요

3배포와 유지보수가 단순하다

scikit-learn 기반으로 모델 저장, Python 추론, 백엔드 연동 구조가 단순하고 안정적

4예측 근거를 제시하기 쉽다

feature importance 를 통해 어떤 입력값이 혼잡도 예측에 영향을 줬는지 설명 가능

여기서 배운 것

모델을 고르는 기준이 숫자 하나가 아니라는 걸 이때 알았습니다. 배포 난이도, 추론 안정성, 설명 가능성까지 같이 놓고 봐야 “운영할 수 있는 모델”이 나옵니다. 0.016 을 포기하고 얻은 게 그거였습니다.

하루짜리행사가기준을바꿨습니다

축제는 하루입니다. 배포하고 나서 고칠 시간이 없고, 장애가 나면 다음 기회도 없습니다. 그래서 이 프로젝트에서는 “가장 잘 되는 상태”가 아니라 “가장 안 죽는 상태”를 기준으로 골랐습니다.

더 정확한 XGBoost 대신 RandomForest 를 올린 것도, AI 가 죽어도 지도·예약·QR 은 돌게 만든 것도 같은 이유입니다. 그리고 실제로 축제장에 올려 보니 내가 예상한 문제와 사람들이 겪는 문제가 달랐습니다 — QA 15명이 짚어준 건 알고리즘이 아니라 버튼 위치와 숫자 읽기였습니다.

KEEP
  • 죽는 걸 전제로 폴백을 먼저 깔기
  • 데이터 흐름 방향을 보고 기술 고르기
  • 만든 걸 실제 현장에 올려 보기
PROBLEM
  • · 학습 데이터가 시뮬레이션이다. HYBRID_SIMULATED(2,520행)로 학습했고, 실제 축제 로그로 재학습하지는 못했다. 예측 정확도의 현장 성능은 아직 모른다.
  • · 운영 검증이 AI Match 한 기능에 몰렸다. 혼잡도 예측과 챗봇은 현장에서 같은 규모로 검증하지 못했다.
  • · 개선 전후를 수치로 남기지 않았다. QA 로 세 가지를 고쳤지만 이탈률·완료율 같은 지표를 재지 않아 “나아졌다”고밖에 말할 수 없다.
