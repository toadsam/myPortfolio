왜 갈랐나

각 시스템이 독립적으로 확장 가능해야 기능을 추가하거나 고칠 때 나머지를 건드리지 않습니다. 실제로 이 구조 덕에 스킬 · 퀘스트 · 포탈을 나중에 각각 따로 얹을 수 있었습니다.

03 · 시점 전환

시점을바꾸면게임이바뀝니다

캠퍼스를 돌아다닐 때는 1인칭이 좋고, 건물에 들어가 싸울 때는 탑다운이 낫습니다. 문제는 카메라만 돌리면 되는 게 아니라는 것입니다. 컨트롤러도, 물리 제약도 같이 갈아 끼워야 합니다. 아래 토글로 바꿔 보세요 — 화면 아래 표가 같이 뒤집힙니다.

PlayerMode.FirstPerson
FIRST PERSON
컨트롤러firstPersonController.enabled = true

둘 중 하나만 켜야 입력이 겹치지 않는다

카메라 부모SetParent(firstPersonCameraParent)

부모를 갈아 끼워야 시점이 튀지 않는다

물리 제약제약 없음

전환 직후 흔들림을 코루틴으로 미뤄 잡는다

1// Desc: 시점 전환 시 컨트롤러/카메라/물리 제약을 함께 스위칭

3{
4 case PlayerMode.FirstPerson:

6 topDownController.enabled = false;
7 mainCamera.transform.SetParent(
8 firstPersonCameraParent, false);

11

enum + switch 로 짠 이유는 하나입니다 — 나중에 모드를 하나 더 추가할 때 case 한 줄만 늘리면 됩니다.

1인칭도 잘 되고 탑다운도 잘 되는데, 바꾸는 그 한순간에만 이상해졌습니다. 원인은 세 가지였고 각각 다른 안전장치가 필요했습니다. 아래 스위치를 꺼 보시면 뭐가 어떻게 깨지는지 보입니다.

세 스위치를 전부 끄고 전환해 보시면, 처음 이 기능을 붙였을 때의 상태가 그대로 나옵니다.

05 · 랜덤 스킬

07 · 몬스터 AI

적은거리하나로판단합니다

복잡한 판단 트리를 만들 수도 있었지만, 플레이어와의 거리 하나로 순찰 · 추적 · 공격을 갈랐습니다. 조건이 명확하면 플레이어도 예측할 수 있고, 나중에 상태를 하나 더 넣을 때 분기 한 줄만 추가하면 됩니다. 아래 초록 사각형을 끌어 보세요.

MonsterAI.Update()Patrol · distance 54.1
밝은 사각형을 끌어서 움직여 보세요
키보드로도 됩니다
MonsterAI.cs실제 코드
1// desc: 플레이어와의 거리값을 기준으로 이동/추적/공격 판단
2void Update()
3{
4 float distance = Vector3.Distance(
5 transform.position, player.position);
6
7 if (distance <= attackRange)
8 { AttackPlayer(); }
9 else if (distance <= detectRange)
10 { ChasePlayer(); }
11 else
12 { Patrol(); }
13}
확장 가능한 AI

상태를 하나 더 넣고 싶으면 조건 분기 한 줄이면 됩니다. 이동은 NavMesh 가 맡고, 이 코드는 “무엇을 할지”만 정합니다.

붉은 원이 attackRange, 노란 점선이 detectRange 입니다. 노란 원 밖으로 나가면 몬스터가 다시 순찰로 돌아갑니다.

08 · 트러블슈팅 02

랜덤은재미있지만불공평합니다

보스가 세 패턴 중 하나를 무작위로 고르게 하면 전투가 매번 달라집니다. 그런데 예고가 없으면 플레이어는 전략을 세울 수가 없고, 그냥 운으로 맞습니다. 아래에서 예고를 꺼 보시면 차이가 바로 느껴집니다.

BossMonster회피 0 · 피격 0

보스가 대기 중입니다

예고가 있으면 랜덤이 「대응할 수 있는 변수」가 됩니다.

BossMonster.cs실제 코드
1// desc: 보스가 공격 시 3가지 패턴 중 하나를 랜덤으로 선택
2void PerformRandomAttack()
3{
4 int attackType = Random.Range(1, 4);
5
6 isAttacking = true;
7 agent.isStopped = true;
8
9 if (attackType == 1)
10 animator.SetTrigger("Attack1");
11 else if (attackType == 2)
12 animator.SetTrigger("Attack2");
13 else
14 animator.SetTrigger("Attack3");
15}
이벤트 기반 판정

데미지는 버튼을 누른 프레임이 아니라 애니메이션의 타격 프레임에서 처리합니다. 그래야 화면에서 보이는 것과 실제 판정이 어긋나지 않습니다.

agent.isStopped = true 한 줄이 중요한 이유 — 공격 모션 중에 NavMesh 가 계속 밀고 들어오면, 예고를 보고 피해도 보스가 따라와서 맞습니다.

09 · UI ↔ 월드

메뉴에서 장비를 골랐는데 게임 안에서 아무것도 안 바뀌면, 그건 그냥 그림입니다. 선택이 실제 게임 오브젝트 상태로 이어져야 플레이가 달라집니다. 캐릭터와 장비에 같은 패턴을 썼습니다 — 아래에서 골라 보세요.

“초기화 없이 적용”으로 바꿔 보시면 왜 먼저 전부 꺼야 하는지 보입니다 — 켜진 게 겹치면 무기가 두 개 달립니다.

12 · 회고

기능이아니라구조를만든프로젝트였습니다

혼자 만드는 게임이라 기능을 빨리 붙이는 게 이득처럼 보였습니다. 그런데 기능이 여덟 개쯤 되니까 하나를 고칠 때마다 다른 게 부러졌습니다. 그래서 중간에 방향을 바꿔 코어 루프와 시스템을 갈랐습니다.

효과는 뒤에서 나왔습니다. 스킬 · 퀘스트 · 포탈은 전부 나중에 얹은 것인데, 얹을 때 전투 코드를 열지 않아도 됐습니다. 시점 전환처럼 여러 시스템을 동시에 건드리는 기능도 enum + switch 한 곳에서 끝났습니다.

KEEP
  • 루프와 시스템을 갈라 두기
  • 조건을 명확히 해서 플레이어가 예측하게 하기
  • Prefab 등록만으로 늘어나는 구조
PROBLEM
  • · 밸런스를 감으로 잡았다. 스킬 수치와 웨이브 난이도를 데이터로 빼지 않아 매번 코드를 고쳐 돌려봐야 했다.
  • · 시점 전환의 지연을 상수로 박았다. 3초는 “해보니 되더라”로 정한 값이고, 왜 3초인지는 지금도 설명하지 못한다.
  • · 플레이 테스트 기록이 없다. 혼자 만들다 보니 남이 어디서 막히는지를 남겨 두지 않았다.
